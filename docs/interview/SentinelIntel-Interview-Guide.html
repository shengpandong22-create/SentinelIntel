1. 项目定位与上游归属

SentinelIntel 不是从零重写资讯平台，而是在 AIHOT 的采集、双评分、写作、事件归组、热点、日报、后台和公开出口之上，增加安防行业配置、三个受控 Agent、证据化产品影响、统一读取层和独立评测体系。面试时应主动说明“基于开源框架做增量工程”，这比模糊归属更能体现大型代码库中的边界控制能力。

如图 1所示，项目亮点不是“堆了三个 Agent”，而是守住了边界：可确定的采集、重试、调度、阈值和持久化仍由 TypeScript 完成；只有语义推理、动态证据获取、时序判断与不确定性处理进入 Python/LangGraph。

30 秒叙事：“我在一个成熟开源内容框架上做了安防垂直扩展。主流水线保持确定性，新建 Python Agent Runtime 只处理研究、跟踪和产品影响；Agent 只能提 proposal，TypeScript 校验 Evidence、置信度和并发版本后提交。项目还有冻结 holdout、回执预算、人工复核和真实 soak test，不是只演示 prompt。”

2. 总体架构与信任边界

图 2中的三条边界是面试重点：① Web 只经 API 读取；② Agent 不直接访问任意 URL/SQL；③公开页面读取数据库时不触发模型调用。这样把“访问网站”和“产生费用/外发数据”彻底分开。

3. Article → Analysis → Fact → Story 的核心数据流

四个词不能混用：Article 是一次采集到的资料；Analysis 是模型对某个 Article revision 的评分和结构化结果；Fact 是可归组的事件事实；Story 是跨来源、跨时间维护的事件容器。Evidence 则是 Agent 结论的可追溯外部依据。

沿图 3从左到右解释即可：先用低成本规则减少无意义调用，再进行独立双评分；只有过门槛的 Analysis 进入写作与结构化；Fact 参与事件关系判断，Story 聚合进展；Agent 是 Story 上的增量 intelligence，不替代主流水线。

4. 事件归组：召回、关系判断、Story 回放

图 4解释了为什么只报一个 accuracy 不够。冻结 holdout 上 Stage A recall@10 为 1.00（60/60），Stage B accuracy 0.75、macro-F1 0.629；Stage C false merge 为 0，但 Story recall 只有 0.095。后者是明确短板，不能被前两项好成绩掩盖。

5. 三个 Agent：相同安全壳，不同长期状态

Security Research Agent

官方来源优先，搜索结果不能直接成为结论；证据不足必须保留 unknown。适合 CVE 不完整、厂商公告缺失或来源冲突。

Event Tracking Agent

维护 why_track、questions、source_targets、next_check_at 与 stop condition。它的价值不是定时器，而是判断“新证据是否构成实质进展”。

Product Impact Agent

LLM 抽取和语义归一，确定性 matcher 判断 exact、比较式、闭区间和有限 union。无法解析的版本表达式进 human review，绝不猜。

共同门禁

high 才能持久化 claim；medium 进复核；low 只保留 unknown。stale version、跨 Story Evidence、缺席推导“不受影响”都会被拒绝。

把图 5和四个卡片一起讲，能避免“Agent 就是多轮 prompt”的误解：真正的工程量在网关、schema、证据、幂等、并发版本与失败恢复。

6. Evidence、proposal 与人工复核

图 6中的关键原则是“unknown 是合法答案”。例如官方公告没写 PoC，系统只能输出 unknown，不能根据缺席推导 no；某个四段厂商版本无法进入闭式 matcher 时，应保存原始表达式和 review reason，而不是让模型猜顺序。

7. 付费请求的回执、预算与恢复

所有付费请求必须经过 receipt。逻辑键把“同一输入、同一模型、同一 prompt/version”的结果绑定起来；已收到的原始响应可复用，避免网络成功但业务提交失败后再次付费。预算由数据库滑动窗口计算，而不是只靠进程内计数。

72 小时运行后，多个并发 Article 会把一个小预算窗口分散到不同阶段，导致回执增加但没有一条原子提交完成。基于图 7，后续实现了 guarded 串行恢复：显式确认 Worker 已停、采集与 Agent 关闭，一次只推进一条，遇 unknown、重复 malformed 或严重 provider failure 立即停止。

8. 统一读取层与公开边界

Story 页面、REST v1 和 MCP 不各自拼装 Agent 数据，而是共同读取 packages/backend/src/publication/agent-intelligence.ts 的投影。这样权限、unknown、Evidence 引用和 review 计数只有一个语义来源。后台可看运行与复核 payload；公开投影只展示允许字段。

安全不变量：浏览页面不触发模型、不访问外网、不创建 receipt；前端不直连数据库；生产环境拒绝开发身份旁路；数据库/API/Python Runtime 不对公网暴露，只有 Web 反向代理出口。

10. 72 小时真实运行：从失败到可恢复运维

试运行使用三个官方信源与 Spark X2.6，采集和模型预算受控，三个 Agent gate 关闭。deadline 快照是 179 条资料、137 analyzed、5 failed、37 waiting；后续在采集关闭状态下串行消化积压，最终 waiting 为 0。两组数字属于不同时间点，不能合并冒充同一时刻。

故障 1：结构化输出

观察到非 JSON、NaN 和异常回执。修复方向是兼容提取、关闭思考/联网扩展、严格 schema 与重复 malformed fail-closed，而不是无限重试。

故障 2：预算拥塞

并发链路共享小预算，出现“receipt 前进但 Article 不提交”。最终采用单链路恢复与精确滑动窗口等待。

故障 3：stale queue job

恢复普通 Worker 后，旧 analyze job 可能把已完成文章降回 new。现在普通任务遇 analyzed/blocked/skipped 直接视为 stale duplicate；管理员显式重评仍允许。

内容质量

MSRC 的 SPA 页面正文命中率显著低于 Cisco/Fortinet，因此增加官方 API/正文提取策略；这是测量驱动的适配器修复，不是泛化重写。

最终数据库运营观察包括 196 analyzed、7 terminal failed；LLM receipts 为 1,035 completed、12 failed、22 received，0 pending/unknown。七天双评分诊断 37 对，平均绝对差 11.54，中位 9，p95 28，5 次跨门槛。这些是运行快照，不是冻结 Evaluation 指标，也不授权直接改 prompt 或 threshold。

TypeScript 主流水线 + Python Agent Runtime复用成熟平台；LangGraph 只处理有状态语义任务不是“全 Python Agent 平台”，跨运行时 schema 要维护
PostgreSQL 关系表，不上 Neo4jMVP 关系可表达，迁移/事务/运维更简单复杂图查询不够自然，但尚无证据需要图数据库
HTTP，不引入 Kafka任务规模和已有 pg-boss 足够；减少部署复杂度极高吞吐与跨服务事件流能力不是目标

闭式版本文法 + 有限 union可测试、fail-closed、避免模型猜版本顺序厂商怪异表达进入人工复核，覆盖率低于“大胆猜测”
三模型 MODEL_REVIEWED无人工裁决者时仍保留独立复核与一致性门槛不能称 human gold，模型知识偏差仍存在

12. 10 分钟面试演示脚本

  1. 第 0–1 分钟：归属。打开本节与图 1，主动说明上游与个人增量。
  2. 第 1–3 分钟：走一条数据。沿图 3解释 Article、双评分、Fact、Story，不先讲 Agent。
  3. 第 3–5 分钟：打开一个 Story。展示 Research、Tracking、Impact 与 Evidence；用图 5解释为何是三个不同状态机。
  4. 第 5–6 分钟：展示人工复核。用一个不支持版本表达式说明图 6的 medium 路由和 unknown honesty。
  5. 第 6–7 分钟：讲费用安全。按图 7解释 exact-key reuse、unknown fail-closed、预算等待。
  6. 第 7–9 分钟：展示 Evaluation。打开 evidence registry，主动指出 Story recall 0.095、样本小和非 human gold。
  7. 第 9–10 分钟：讲生产事故。用 72 小时 soak 的三类故障与修复收尾，说明你不仅“写功能”，还把系统运行到暴露真实问题。
演示前检查：模型与采集默认关闭；演示数据有明确标识；后台鉴权有效；不要现场启动付费评测；准备好离线 HTML 和冻结报告，网络不可用也能讲完整。

13. 高频追问与可防守回答

为什么不用一个大 Agent 完成所有步骤？
采集、重试、预算、阈值和持久化都可确定测试，交给 Agent 会降低可预测性。Agent 只负责语义研究、动态工具选择、时间变化和不确定性。
为什么不直接让 Python 写数据库？
跨运行时 proposal 先经过 TypeScript schema、Evidence scope、stale version 与 confidence gate，再事务提交。这样模型或 Python bug 不会越过核心业务不变量。
三模型复核算人工标注吗？
不算。仓库明确标为 MODEL_REVIEWED、humanGold=false；它比单模型标签强，但仍可能共享知识偏差。
你最不满意的指标是什么？
事件归组 Stage C Story recall 0.095。候选召回和 false merge 控制不错，但拆分偏保守。下一步应在 development 上定位 relation→merge 策略，而不是改已消费 holdout。
如何避免重复扣费？
请求有稳定 logical key，回执保存原始响应。received 可在相同 key 下继续解析/提交；unknown 因扣费状态不明而 fail closed。
为什么版本匹配不用 LLM？
版本顺序和区间是确定性语义。LLM 只抽取原始表达，matcher 处理闭式文法；不支持就进 review，避免“看起来合理”的错误覆盖范围。
项目真实吗？
有真实公开信源、Docker 部署、72 小时运行、回执/预算故障和积压恢复；但没有真实企业资产、外部付费用户或大规模 human gold，应如实说明。

14. 从不会源码到能讲原理的学习路线

  1. 第一遍（30 分钟）：只看图 1–3，能用自己的话说出归属、双运行时和四层数据模型。
  2. 第二遍（45 分钟）：看图 4–7，画出 grouping 三阶段、Agent proposal 和 receipt 状态机；不要背类名。
  3. 第三遍（45 分钟）：读图 8 与指标表，练习区分 metric、denominator、label provenance、reproducibility。
  4. 第四遍（30 分钟）：按 10 分钟演示脚本完整说一遍，录音后检查是否主动讲了上游、限制和失败。
  5. 第五遍（按需查源码）：只为追问打开 Evidence 矩阵对应文件，确认细节，不从目录树开始漫游。
